# Kachka release candidate · 24 November 2026

**Decision: not yet release-ready for public distribution.** The branch is ready for code review and isolated staging. Its scored sensor experience still lacks phone and reference evidence. The production revision, room durability, safe rollback image and commercial permissions need owner verification. Merging to main requests a deployment, so hold the merge. A restricted adult beta could be reconsidered after the operational, privacy and native-phone gates below, with measured pulse excluded from scoring unless its pilot passes. That restriction would need implementation and verification before offering such a build.

The fetched and rechecked main was `0dbcbf15c3cff6c84a67de3269e1bdef65509b1b` (PR #62). ## Engineering and user journeys

- On main, a client requesting Brotli received the entire 521,300-byte JS asset; an expired JS URL received HTTP 200 and the SPA shell. The build now produces Brotli variants for JS and CSS. The server negotiates representations, varies cache keys, returns 404 for missing assets and keeps deep links working. No routes became on-demand downloads. The measured cold-load improvement and the open-page offline test favour this approach for this RC. The minified entry still exceeds Vite's 500 kB warning and still costs parsing time.
- Stand Still left a real Chromium AudioContext running at least 4.5 seconds after replay appeared. The regression test failed on the old code. The context now closes when the final cue ends, or immediately if that cue cannot play. Cancellation and unmount retain cleanup. No acquisition threshold, score, audio composition, animation or visible instruction changed.
- The example deployment and absent-variable default now select built-in Dr. Bin Chicken commentary. Explicit server enablement, a server key and a positive daily allowance are required for paid calls. Leave the key absent, `VERDICT_ENABLED=false` and `VERDICT_DAILY_CALL_LIMIT=0`. An existing explicit true/positive production configuration requires operator review. No provider calls or billing changes were made.
- Docker reads the health port from the configured listener port. Image-baked revision takes priority. Builders without Git refs may inject the checked-out full SHA as build argument `BUILD_REVISION`; a stale runtime label cannot fix an unknown image. Main CI now follows a successful Dokploy webhook with a bounded public health check for no-store and the matching SHA. A timeout makes the deploy job fail visibly, with no automatic rollback. A single healthy response cannot establish topology, durable storage, or sustained uptime.
- First visit, quick demo, personal baseline, actual app Choice Tap with synthetic inputs, skip/retry, recalibration, migration, historical tickets, drink edits/undo, missing quantities, field guide and all three caffeine scenarios passed in Chromium. The alcohol safety rule runs for the ticket and export, including a later alcohol entry on a stored Steady result. Export optional fields are off initially. There is no BAC estimate, clearance time or personal sleep forecast. The matrix and evidence limitations apply to the playful labels and provisional comparison thresholds. [Science and sources](PHASE-G-COMMERCIAL.md) · [Phase D evidence ledger](research/PHASE-D-EVIDENCE.md)
- Watching the public board did not join it. A separate preview and deliberate action were required to publish. Failed publication, withdrawal 503, offline erasure followed by reload/retry, failed storage writes and cross-tab revocation passed. The app retains a pending removal handle while locally erasing personal records when withdrawal is unconfirmed. Presence expires after 45 seconds. A renewed 12-hour Redis key TTL, application pruning and backup retention have different meanings. A recipient's downloaded PNG cannot be recalled. [Room design and residual risks](PHASE-F.md) · [Threat model](THREAT-MODEL.md)

**Public score decision.** Keep the documented response contract for this candidate. A publisher sees nickname, word, score and provenance before sharing; the public projector omits the number and ranking arrays are empty. Removing the required score field would break parsers using the existing contract. Adding a score-free endpoint alone would leave the score publicly retrievable. For consumer launch, identify client owners and supported versions, stop collecting numeric scores for future shares under a versioned contract, agree the retirement date, then close the old read/write path and expire legacy rows. Until then, explicitly disclose that API readers can see the score. No API migration or new room features were introduced here.

The already-loaded page entered Quick demo offline in all six contexts. The manifest supports standalone presentation, but the app has no service worker for guaranteed cold offline startup. ## Staging, production verification and recovery

1. **Identify the current deployment.** Dokploy → Projects → Kachka → application → Deployments. Open the last successful deployment, record commit, finish time, build result and image digest. Under Containers or the service task list, record healthy/running count, restart count, events and configured target port. In Logs restrict review to startup/shutdown and mirror status events. Report only revision, counts, health, timestamps and error classes. In Domains confirm the host is kachka.fun, the backend port matches PORT (default 3333), and TLS is active. From an approved network open https://kachka.fun/api/health and compare its SHA with the deployment commit. The owner's reported CI/webhook success for PR #62 is the available production evidence.
2. **Confirm recording and withdrawal topology.** Dokploy → application → Environment. Inspect presence only of REDIS_URL, VERDICT_ENABLED, VERDICT_DAILY_CALL_LIMIT, ANTHROPIC_API_KEY, TRUSTED_PROXY_IPS and ROOM_ADMIN_TOKEN. Compare the redacted hasRedis flag with Redis service health and mirror connection events. If Redis is absent, document that the board is volatile. If present, open Redis service → network, persistence and backups. Confirm private connectivity, TLS where appropriate, dedicated ACL/keyspace, authenticated access, AOF or provider persistence, retention and deletion handling. A healthy app or configured URL alone does not verify Redis. Use one active app process. Check service deployment order, overlap during replacement and termination grace exceeding 10 s. Choose stop-first or otherwise exclude overlapping writers, accepting brief unavailability.
3. **Check the edge privately.** Cloudflare → domain → DNS → Records: confirm the production hostname points to the intended proxy path. SSL/TLS → Overview and Edge Certificates: verify Full (strict), valid origin certificate, HTTPS redirect and actual HSTS policy. Caching → Cache Rules: confirm /api/* bypasses edge caching, including room and health. Check delivered response headers with a HEAD request, e.g. `curl -sSI https://kachka.fun/api/room`; require no-store and no cache hit. In Dokploy → Domains/Traefik and the host firewall, verify who can reach the origin, the app's immediate socket peer and how every hop handles forwarded headers. Leave TRUSTED_PROXY_IPS empty until isolation and exact immediate peer IPs are established. Do not guess addresses from DNS or trust a Docker subnet. Keep private topology with the operator.
4. **Exercise isolated staging.** Build the proposed SHA on an isolated HTTPS hostname with its own ACL, Redis and disposable volume. Never copy production Redis or user records. Keep paid AI off. Run the health verifier with the full SHA, confirm one process and absence of stale HTML on expired asset URLs. With two fresh browser profiles, use synthetic names: watch, join, preview, publish one simulated ticket each, turn one off, verify removal and the control. On that dedicated staging Redis stop service, verify withdrawal is unconfirmed and sharing stays off, restore service, retry and require acknowledgement. Restart Redis and the app, confirm only the control remains. Check offline Start over → reload → retry and native receipt saving. Use the physical pilot only after consent and separate plan approval. [Device instructions and gates](phase-g-device-pilot.md)
5. **Rehearse failure before approving merge.** Retain the immutable digest and config of a proven Phase F-or-later image. On staging interrupt a candidate before it becomes healthy. Verify the public check fails or remains pending, no second writer is active, alerts reach the operator and the previous privacy-safe image can serve the same staging domain. Verify revision, a new explicit ticket, a pending withdrawal and the control row after recovery. Record downtime, revision, image, operator and time to recover. A deployment cancellation does not cancel an accepted webhook.
6. **Approved deployment only.** Review the full diff and passing PR CI. Main push runs checks/build, then POSTs the Dokploy webhook and polls public health. Record actual merge SHA, build digest, task transition and matching healthy SHA. Monitor 429/5xx, health failures, restarts, mirror errors and withdrawal 503s, resource use, provider attempts and unexpected cost through one representative usage window. Use aggregated counters and event classes. Keep request bodies, names, handles, IPs and credentials out of reports.
7. **If rollout or privacy verification fails**, stop publishing/serving the room at ingress if required, preserve outstanding deletion handles and disable paid calls. Inspect deployment status before any retry. Recover to the verified Phase F-or-later digest only if it preserves explicit intent, empty rankings and pending deletion. Otherwise keep the service in maintenance and forward-fix. Never restore an old room backup that could republish withdrawn data. Verify health, single instance and synthetic withdrawal again before reopening. Reverting to Phase E can restore automatic posting and ranking. There is no Redis schema migration in this RC.
